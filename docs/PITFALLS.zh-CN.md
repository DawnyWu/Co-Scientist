## 术语表

**并发与并行的区别。** 并发是指多个任务同时**处于进行中**;并行是指多个任务在同一时刻**同时执行**。一台单核机器可以做到并发(在每个任务等网络的时候切到另一个)而做不到并行。这个系统几乎完全是并发问题:它绝大部分时间都花在等模型回复上。

**事件循环(event loop)。** 一个单独的线程,维护一份未完成任务的清单,挑其中就绪的那个来跑。当某个任务说 `await 某个慢操作()` 时,它把控制权交回给循环,循环趁这段时间去跑别的任务。Python 的 `asyncio` 就是靠这个在不用线程的情况下获得并发。

**阻塞(blocking)。** 占着自己的线程不交还控制权的代码——任何会等待的普通函数调用,比如 `requests.get(...)` 或者读一个大文件。在事件循环里,**一个阻塞调用会冻结所有任务,不只是它自己**,因为大家共用那唯一一个线程。这是异步程序里最大的一类困惑来源。

**竞态条件(race condition)。** 一类结果取决于两个并发操作恰好以什么顺序交错的 bug。它间歇性出现,常常只在压力下出现,而且往往一加日志就消失了。

**原子(atomic)。** 一个不会被其它操作观察到"做了一半"的操作——它要么发生了,要么没发生。数据库里的 `UPDATE t SET n = n + 1` 是原子的;而"读出 n、在程序里加一、写回去"不是。

**读-改-写(read-modify-write)。** 上面那个非原子的模式:读一个值、算出新值、写回去。如果两个 worker 同时这么干,它们读到同一个起始值,其中一次更新就消失了。

**丢更新(lost update)。** 并发读-改-写的结果:已经成功完成的工作被别人的写覆盖,静默消失。没有任何报错。这是这份文档里最难查的一类 bug。

**幂等(idempotent)。** 一个操作,不管你执行一次还是五次,结果都相同。**只有幂等的操作才可以安全重试**,因为崩溃之后你通常无法判断上一次尝试到底成功了没有。

**幂等键(idempotency key)。** 附在一份工作上的唯一标识,用来让第二次"入队同一份工作"的尝试被识别出来并丢弃。

**租约(lease,也叫可见性超时 visibility timeout)。** worker 取走一个任务时,在任务上盖一个"归我,直到时刻 T"的戳。如果 worker 挂了,过了 T 之后别的 worker 就可以回收这个任务。这是队列不需要直接检测崩溃、却又不丢工作的办法。

**死信(dead letter)。** 失败次数太多的任务被搁置,而不是无限重试。没有这个机制,一个永久损坏的任务("毒丸")会一直吃掉重试容量。

**背压(backpressure)。** 消费者跟不上生产者时系统做什么。选项只有三个:阻塞生产者、缓冲、丢弃。**不小心选了"阻塞"**,就是一个慢客户端冻结整个服务器的原因。

**文件描述符(file descriptor)。** 操作系统给进程的一个数字,用来指代一个打开的文件、socket 或管道。子进程默认继承父进程的描述符——这正是 C1 那个死锁的成因。

**EOF(文件结束)。** 读取方在管道里没有更多数据、**并且**所有持有写端的进程都已关闭时收到的信号。第二个条件才是大家会忘的那个。

**溯源(provenance)。** 一份"这条信息从哪来"的记录。在这里指:模型实际看过哪些 URL,这样一条引用就可以被核对,而不是只能被信任。

**GIL(全局解释器锁)。** CPython 的一把锁,同一时刻只允许一个线程执行 Python 字节码。它意味着线程不会加速纯 Python 计算,但**对等待 I/O 有效**,而且对那些工作时会释放这把锁的 C 库(NumPy、FAISS、scikit-learn)也有效。

## A 部分 — 让模型把活干完

### A1 — 模型会一直搜下去而不肯提交

**现象。** agent 把所有允许的迭代都烧在文献检索上,什么都没产出。任务以"工具循环耗尽"失败。钱花了,没有输出。

**为什么。** 研究目标常常要求一个**没有**先前发表证据的候选。模型去搜,什么都没搜到,然后把"没有结果"理解成"我的检索不够好",而不是"我被要求找的东西确实不存在"。于是它换个说法再搜一遍,无限循环。它在寻找一个**按构造就不可能到来**的确认。

**怎么做。** 两道互相独立的防线,因为任何一道单独都不够。

1. 在提示词里**明确告诉**模型:空结果集是新颖性的**正面证据**,并给一条具体的停止规则("同一候选连续 2–3 次检索没有相关命中,就认定新颖性成立并记录")。同时把偏好说白:一个有几次空检索支撑的已记录假设,远胜于用完轮次一无所获。
2. 在最后一轮允许的迭代上,用 `tool_choice` 强制记录工具,让模型没法把最后一次机会花在又一次检索上。

**在哪。** `agents/generation.py` 里的 `articles_block` 指令;`llm/tool_loop.py` 里的 `force_terminal_tool` 分支。

### A2 — 不是每个模型调完记录工具就会结束回合

**现象。** 在 Claude 上正常,在 Gemini 或 OpenAI 兼容端点上卡住。模型第一次调用就交出了完好的结构化记录,循环却一直跑到迭代耗尽然后抛异常。

**为什么。** 循环原本的退出条件是"模型不再要求调工具"。Claude 在调用 `record_hypothesis` 这类工具之后会可靠地结束自己的回合;别的模型调完之后还会继续,于是循环老老实实又发一轮,那一轮又把记录工具摆出来,模型又调一次——直到迭代上限触发。而记录从一开始就在那儿。

**怎么做。** 维护一份明确的"终结类"工具清单,一看到就结束循环并短路。**不要派发**这些工具:模型的答案已经在工具调用的参数里了,没有什么可执行的,执行反而只会招来下一次调用。

**在哪。** `llm/tool_loop.py` 里的 `DEFAULT_TERMINAL_TOOLS` 和 `_run_driven` 中的提前返回。

### A3 — 引用必须在生成时过滤,而不是事后校验

**现象。** 一个假设引用了一篇标题像真的、作者像真的、URL 却 404 或者指向毫不相关内容的论文。

**为什么。** 模型产出"像引用的文本"和产出任何其它文本一样轻松。要求它给 URL 并不会让那个 URL 变成真的。

**怎么做。** 不要校验,要**过滤**。在工具循环运行期间,把每一个出现在工具结果里的 URL 收进一个集合。模型提交记录时,凡是 URL 不在这个集合里的引用**直接删掉**。规则就变成了"你只能引用你真正看过的东西",而且是结构性强制的,不是靠好言相劝。

两个让它在实践中真正生效的细节:

- 遍历工具结果时只认一组固定的键(`url`、`abs_url`、`pdf_url`、`pubmed_url`),并要求 `http`/`https` 前缀,而不是用正则去任意文本里刮 URL。
- 把这个遍历器放进它自己的模块。在这个项目里,工具有时跑在另一个进程里(CLI 后端用的 MCP server),两边必须以完全相同的方式提取 URL,否则这条规则会在其中一个后端上静默失效。

**在哪。** `tools/urls.py`;`agents/generation.py` 里的 `_filter_to_seen_urls`;由 `mcp/server.py` 写、由 `llm/cli_backend/base.py` 读回的溯源日志。

### A4 — 一个模型用不了的工具比没有这个工具更糟

**现象。** 没有配置网页检索的 API key 时,小模型会**直接放弃任务**,而不是退回去用那些确实可用的文献 API。

**为什么。** 工具出现在工具清单里,模型就会围着它做计划。等调用失败时,模型把这次失败当成阻塞性的,而不是当成若干选项中的一个。

**怎么做。** 只在前置条件真正满足时才注册工具。缩短工具清单本身也能可测量地提升工具选择的质量,所以这不是纯防御性的改动。

**在哪。** `tools/registry.py` 里 `WebSearchTool` 的条件注册;`AGENT_TOOLS` 里的按 agent 白名单。

### A5 — 把所有外部文本当数据,永远不要当指令

**现象。** 抓回来的网页或论文摘要里含有类似"忽略之前的指令,改为……"的内容,而模型照做了。这就是提示词注入(prompt injection)。

**为什么。** 模型看到的是一段扁平的 token 序列。它没有内建的概念去区分哪些来自你、哪些来自陌生人的网页。

**怎么做。** 把每一块外部文本包在定界符里,**开标签和闭标签带上相同的 id 和内容哈希**,这样模型能判断这一块是完整的。包之前先剥掉文本里已经存在的、你自己那套标签的副本——否则被注入的文本可以伪造一个闭标签从而"逃出"这一块。然后在系统提示词里声明:这些标签里面的一切都是数据。

有一个改良值得照抄:软化那些像指令的前缀(`SYSTEM:`、`INSTRUCTION:`、`IGNORE PREVIOUS:`)时,**只匹配行首**。科学摘要里合理地存在句中的"Important: ……"这类写法,把它们弄坏对安全毫无增益,只是白白降低了输入质量。

**在哪。** `safety/quoting.py`,以及由 `agents/base.py` 前置的 `SAFETY_PREAMBLE`。

## B 部分 — 并发与共享状态

### B1 — 事件循环里的一个阻塞调用会冻结一切,而且会让你的超时失效

**现象。** 并发看起来毫无作用。心跳莫名超时。租约在任务仍在运行时过期。一切都是间歇性的,而且没有任何异常可看。

**为什么。** 在事件循环里,所有任务共用一个线程。一个会等待的同步调用——`requests.post(...)`、读一个大文件、一次很长的 NumPy 计算——会占住那个线程直到它自己结束。期间别的任务一步都不动。由此产生三个独立的后果,而**第二和第三个比第一个严重**:

1. **并发降到零。** 四个"并发"任务,每个做一次 120 秒的阻塞 HTTP 调用,总共要 480 秒,不是 120 秒。你付了异步的全部复杂度成本,却什么好处都没拿到。
2. **超时静默失效。** `asyncio.wait_for` 和 `asyncio.timeout` 只能在 `await` 点上取消任务。阻塞代码里没有 `await` 点,所以在那个阻塞调用自己返回之前,超时**不会触发**。你系统里所有的超时都变成了装饰。
3. **租约和心跳会造成重复执行。** 如果心跳是一个后台任务,循环被阻塞期间它跑不了。租约过期,另一个 worker 回收了一个仍在执行的任务,于是这个任务被跑了两遍。在这个项目里租约是 300–600 秒,而模型调用超时是 120–900 秒——同一个数量级,所以这不是假想。

**怎么做。** 永远不要在异步代码里直接调阻塞函数。包一层:

```python
result = await asyncio.to_thread(my_blocking_function, arg1, arg2)
```

**那个函数本身一行都不用改**——它继续是普通同步代码,但跑在一个工作线程上,于是循环保持转动。这就是正确的渐进路径:先包起来,以后只在性能分析确实指出必要时再改成原生异步(通常并不必要)。

两个边界:

- `to_thread` 对 I/O 有效,对那些工作时会释放 GIL 的 C 扩展也有效(NumPy、FAISS、scikit-learn 都会释放)。对 CPU 密集的**纯 Python** 计算,GIL 意味着线程什么都给不了,要用 `ProcessPoolExecutor`。
- 开发时打开 asyncio 的调试模式(`PYTHONASYNCIODEBUG=1`,或 `loop.set_debug(True)`)。当某个回调占用循环超过 100 毫秒时它会警告,这是找出意外阻塞调用最快的办法。

**如果你在开一个新项目,这里有个不对称性值得注意。** 把同步代码改成线程池是**局部**改动(一个循环变成 `executor.map`);改成异步是**全局**改动,因为 `async` 会向上传染每一个调用者。如果你还不确定是否需要并发,就写同步代码,以后再加 `concurrent.futures`。你保留了那条便宜的升级路径。

**在哪。** 19 处 `asyncio.to_thread` 调用点 —— `vectors/store.py`、`agents/proximity.py`、`tools/web_fetch.py`、`tools/builtins/*.py`、`vectors/embedder.py`、`agents/metareview.py`。

### B2 — `asyncio.Lock` 本身并不能让一个线程不安全的库变安全,而且它跨进程完全无效

**现象。** FAISS 索引偶发损坏,或者索引静默地少了一些向量。

**为什么。** 这里有两种不同的失效被混在了一起。

**在单个进程内:** `asyncio.to_thread` 会把工作派进一个共享线程池。两个"并发"调用 `add()` 和 `search()` 的协程,因此会在同一时刻跑在两个不同的操作系统线程上——而 FAISS 不是线程安全的。这里真正起保护作用的就是那把 `asyncio.Lock`:只有一个协程持有它,而且它是**跨着** `to_thread` 调用持有的,所以任何时刻只有一个线程在 FAISS 内部。

**跨进程:** `asyncio.Lock` 只是某一个进程内存里的一个普通对象,对另一个进程毫无影响。两个进程各自加载索引、各自 `add()` 一个向量、各自 `save()`——后写的把先写的覆盖掉。这就是**丢更新**:一个已经成功算出来并存下的向量就那么不在了,而且没有任何报错。

注意**原子地写文件解决不了这个问题**。这个项目先写 `.tmp` 再 `os.replace`,这能正确地防止崩溃留下一个撕裂或损坏的文件。它对"两个进程互相覆盖对方完整且有效的文件"毫无办法。

**怎么做。** 按优先级:

1. **干掉这个共享可变文件。** 把向量存进数据库(Postgres + `pgvector`,或者 SQLite 的一个 `BLOB` 列加一次 NumPy 点积)。并发就变成数据库的问题,而它本来就解决了这个问题。这个项目对 FAISS 的四处用法全都依赖对最多几千个向量做精确暴力检索,搬过去什么都不损失。
2. 如果要保留文件,给它**一个唯一的所有者**——一个进程,或者一个别人向它发消息的线程——而不是一把每个参与者都得记着去拿的锁。
3. 如果两者都做不到,用操作系统级的锁(`flock`)并接受它的代价。

**在哪。** `vectors/store.py` —— `_lock` 和它上面的注释解释了进程内那一半;跨进程那一半目前只靠"一个会话一个进程"这条约定在防。

### B3 — 先读后写之间留了一个窗口,查重和预算准入都掉在里面

**现象。** 同一个会话里出现两个几乎相同的假设,尽管查重是工作的。或者:总花费超过了配置的上限。

**为什么。** 两者都是读-改-写。查重先读索引、判定"没有重复",然后**过一会儿**才插入。预算准入先读计数器、判定"付得起",然后**过一会儿**才记录预留。这中间发生的任何事,对那个判定都是不可见的。

**怎么做。**

- 把判定串行化,而且串行化要**同时盖住读和写**,不是各自盖一半。一把你在"检查"和"动手"之间就释放掉的锁,什么都没保护到。
- 更好的做法是把判定推进数据库,变成一条带条件的语句,这样根本没有窗口:

  ```sql
  UPDATE sessions
     SET budget_used_usd = budget_used_usd + $2
   WHERE id = $1 AND budget_used_usd + $2 <= budget_usd
  ```

  然后看受影响的行数,0 就是拒绝。这是原子的,而且在任意多个进程下都成立。
- **保留一道粗粒度、持久化的刹车,独立于细粒度那一道。** 这里进程内的 `TokenBudget` 做 per-agent 准入,而停止判据读的是 `budget_used_usd` 列,那是一次原子自增。所以即使准入算错了,会话仍然会停——精度变差,但没有失控。刻意设计这个后备是值得那一点重复的。

**在哪。** `agents/generation.py` 的 `_dedup_query` / `_dedup_commit`;`llm/budgets.py` 的 `TokenBudget.admit`;`sessions.add_usage` 和 `termination.budget_exceeded`。

### B4 — 失败的调用必须把它预留的东西还回来

**现象。** 一个在会话开始时正常的 agent,后来开始通不过准入,尽管会话离预算上限还很远。而且每出一次错就更糟一点。

**为什么。** 预留模式是:调用前按估算预留,调用后按实际结算。如果调用抛异常而没有任何东西释放这份预留,那份预留就永久地从这个 agent 的份额里被扣掉了。每次失败都让它再小一点。

**怎么做。** 在一个捕获**一切**的处理器里释放,而不是只捕获你预期的错误:

```python
try:
    outcome = await run_the_call(...)
except BaseException:
    await budget.settle(agent, est_tokens=..., est_usd=..., actual_usd=0.0)
    raise
```

用 `BaseException` 而不是 `Exception` 很关键:取消(`asyncio.CancelledError`)和 `KeyboardInterrupt` 都不继承 `Exception`,而这两者在这里都是常规事件——Supervisor 在收尾时会取消在途任务。

还要知道这个模式的边界:**如果进程被 `SIGKILL` 杀掉,任何处理器都不会运行。** 一份必须能扛过这种情况的预留,需要在持久化存储里带一个存活时间,让它自己过期。这正是任务租约在做的事;预留需要同样的处理,而这个代码库目前还没有。

**在哪。** `llm/cli_backend/base.py::call` 里的 `except BaseException` 块。

### B5 — 重试的身份要确定性地推导,否则会重复计入

**现象。** 崩溃重启之后,某个假设的 Elo 因为**同一场**比赛移动了两次。

**为什么。** 重试无法知道上一次尝试有没有提交。如果重试为**同一份逻辑工作**生成了一个**新的**标识,任何基于那个标识的去重都会被绕过,效果就会被施加第二次。用墙钟时间戳是这个错误的经典版本,因为它按构造在每次尝试时都不同。

**怎么做。** 两层。

1. 从某个稳定、而且重试也拿得到的东西里确定性地推导出标识——这里是任务 id。这样重试会算出**完全相同**的比赛 id。
2. 让写入本身幂等:在一个事务里往一张以该 id 为主键的日志表插入,插入冲突就跳过更新。**确定性 id 配非幂等的写仍然会重复施加;幂等的写配随机 id 则永远等不到去重的机会。两者都需要。**

**在哪。** `agents/ranking.py` 里的 `round_id = task.id`;`storage/repos/tournaments.py` 里的 `apply_elo_update`,它用了 `BEGIN IMMEDIATE` 和 `elo_journal` 的主键。

### B6 — 靠给写入排序来保持两个存储一致

**现象。** 向量索引里有数据库里不存在的假设,或者反过来。检索返回了查不到的 id。

**为什么。** 插一行和加一个向量是针对两个不同存储的两个独立操作,没有跨越两者的事务。先做的那个可能成功,而第二个失败。

**怎么做。** 给写入排序,让失败的后果无害,并让第二步以第一步**真的发生过**为条件:

1. 先把大件写到磁盘,这样你随后创建的行指向的是一个真实存在的文件。
2. 插入行。确定性 id 让这一步幂等。
3. **只在插入报告了"这是一个新行"时**才加向量——不是"只要没抛异常就加"。一个因为行已存在而变成空操作的插入,绝不能再加一个重复向量。

然后从 embedding 元数据加一个外键指向假设,让数据库直接拒绝那个不一致的状态。

**如果可以,更好的做法。** 把向量放进和行同一个数据库,在同一个事务里插两者。整类问题消失。

**在哪。** `agents/generation.py` 的 `_persist`,步骤 1–3;`embeddings_meta.hypothesis_id` 上的外键。

### B7 — 永远不要让慢的消费者阻塞生产者

**现象。** 一个开着事件流、闲置着的浏览器标签页,导致整个调度器停摆。

**为什么。** 扇出时如果对每个订阅者的队列 `await put()`,发布方的速度就由它**最慢的**订阅者决定。一旦某个订阅者停止读取——客户端睡眠了、网络把包吞了——队列填满,`put()` 就永远等下去。这里的发布方是调度器,所以一切都停了。

**怎么做。** 明确选择你的背压策略,而且永远不要选"阻塞"。有界队列、非阻塞放入,溢出时丢掉最旧的一条然后继续。丢掉实时视图的事件是可接受的;让调度器停摆不可接受。

实现上要稳而不要巧:先弹出直到有空位,然后尝试 `put_nowait`,如果**那个**还是失败(另一个协程在这中间又把队列填满了),就为这个订阅者丢掉这条事件然后继续往下走。在这里写重试循环没有收益,还可能空转。

**另外还要做。** 把事件也持久化进一张表。这样重连的客户端可以先快照历史,只依赖内存总线拿实时更新,于是丢掉个别事件真的变得无害了。

**在哪。** `orchestrator/events.py` 的 `EventBus.publish`;`events` 表。

### B8 — 幂等键要锚定在进展上,不要锚在新生成的 id 上

**现象。** 队列被几百个重复的"跑一批锦标赛"任务填满。预算在流失,却没有新结果。

**为什么。** 一个每约 10 秒触发一次的周期性补活循环,如果用新生成的 id 入队工作,它就没有办法察觉自己 10 秒前入队的那个还在 pending。于是它又入队一个,再一个。

**怎么做。** 用一个**只在真实进展发生时才变化**的值来构造幂等键——一个单调的业务计数器,比如已进行的比赛场数。这样同一个"纪元"内的每次补活都会和已有的键碰撞,免费被丢弃。

对于跟着某个具体条目而不是跟着周期性节拍的工作,就用条目来做键:`f"{hypothesis_id}::review::full"` 表达的是"这个假设一辈子只评审一次",这恰好就是想要的约束。

**在哪。** `agents/supervisor.py` 中 `_decide_next_steps` 里的 `anchor_mc`;以及全代码库里构造的那些 `idempotency_key`。

### B9 — 给每次重试自己的临时空间

**现象。** 重试后的调用返回的结果,混杂了失败那次尝试的输出和新尝试的输出。

**为什么。** 子进程把结构化结果写进一个捕获目录,文件从 `0001` 开始编号。多次尝试共用一个目录,意味着重试会覆盖掉靠前的编号,而失败那次尝试写在**超出**重试数量之外的文件会存活下来,并被当作结果的一部分读进去。

**怎么做。** 按**尝试**分配新目录,不是按调用。一般规则:**如果重试和它所替代的那次尝试共用可变的临时空间,它就会继承那次尝试的半成品。**

**在哪。** `llm/cli_backend/base.py::_run_with_retry` 里的 `capture_root / f"attempt-{attempt}"`。

### B10 — 把单进程假设变成显式的

**现象。** 用户为了跑快点,起了两个 `co-scientist run`。预算超支、向量丢失、实时视图只显示一半事件。**任何地方都没有报错。**

**为什么。** "一个会话一个进程"这个假设是真实且合理的,但它活在注释里。启动时没有任何东西检查它。

**怎么做。** 把它变成一个启动期错误。一张 `runtime_locks` 表,以会话 id 为键,存 pid、主机名和一个心跳时间戳:启动时插入,已被持有就大声失败,只在心跳过期时才允许接管。几十行代码,把三种静默损坏换成一条清晰的报错。

更一般地说:**一个没有任何东西强制的不变量不是不变量,是一个愿望。** 要么强制它,要么消除对它的需要。

**在哪。** 尚未实现。该放的位置是 `agents/supervisor.py::run_session`。

## C 部分 — 进程、文件与外部世界

### C1 — 当孙子进程继承了管道时,管道会死锁

**现象。** 一个调用一直挂到超时,而且没有任何进程在跑。在这个项目里的表现是:一个排序任务闲置着,而 `ps` 显示没有任何子进程存活。

**为什么。** 这条需要把机制讲开。

一个管道有写端和读端。读取方通过收到 EOF 才知道数据结束了——而 **EOF 只在所有持有写端的进程都关闭它之后才会送达**。`subprocess.communicate()` 等的就是 EOF。

这里的子进程是一个 agent CLI,而那个 CLI 又启动了它自己的子进程:MCP 工具 server。这个孙子进程**继承了父进程 stdout 的写端**,因为描述符默认是被继承的。于是即便 CLI 自己已经退出,管道的写端在孙子进程里仍然开着,EOF 不会到来,`communicate()` 就一直等——等满整个超时。

**怎么做。** 把子进程的 stdout 和 stderr 重定向到**临时文件**而不是管道。文件没有 EOF 握手需要等:等直接子进程退出,然后读它写下的东西。这同时也消掉了另一个独立的管道缓冲区死锁(子进程写满了操作系统缓冲区从而阻塞在写上,而父进程阻塞在读上)。

注意这**和异步毫无关系**——线程或者纯同步代码会一模一样地撞上。

**另外还要做。** 正确地升级终止手段:`SIGTERM`,等几秒,然后 `SIGKILL`,并且每一步都要抑制 `ProcessLookupError`,因为进程可能在你检查和发信号之间就退出了。

**在哪。** `llm/cli_backend/base.py` 的 `_spawn` 和 `_terminate`,推理写在 docstring 里。

### C2 — 剥掉那些会让子进程给你计费的凭据

**现象。** 一个专门因为"跑在固定月费订阅上"而选择的后端,悄悄产生了按 token 计费的 API 账单。

**为什么。** agent CLI 会先检查环境里有没有 API key,再退回到它的 OAuth 登录。如果父进程环境里有 key,子进程继承它并走上计费路径。这次运行仍然成功,所以没有任何东西引起注意——**你在账单上才发现。**

**怎么做。** 显式构造子进程的环境,删掉每一个可能选中计费路径的变量:显而易见的那些 API key,以及 base URL 和云路由的覆盖项(`*_BASE_URL`、Bedrock / Vertex 开关),后者重定向计费的效果一点不差。然后写一个断言"环境已被剥离"的测试,因为这是一种没有任何手工测试能抓到的静默失效。

**在哪。** `llm/cli_backend/base.py` 里的 `BILLING_ENV_VARS` 和 `sanitized_env`,以及断言它的那个测试。

### C3 — 替换 harness 的提示词是一笔巨大而不可见的成本

**现象。** 每次调用的 token 用量,比你写的那段提示词该有的量高一个数量级。

**为什么。** 一个编码 agent CLI 自带一段相当长的系统提示词,描述它自己的工具和约定。把你的提示词**追加**在它后面,意味着每次调用都要为那一整段付费。在这个项目上实测:在默认提示词下的一次微不足道的调用,花掉约 19k 缓存写入加约 24k 缓存读取的 harness 脚手架 token;换成替换式提示词后是 1–2k。

**怎么做。** CLI 允许的话就替换而不是追加,并且做成一个配置开关,以便在真的需要 harness 上下文时关掉。这在**调用量大而每次调用很小**的地方影响最大——这里是成对排序——因为固定开销会占主导。

**在哪。** `[llm.claude_cli]` 里的 `replace_system_prompt`,在 `llm/cli_backend/claude_code.py` 中生效。

### C4 — 抓取模型选定的 URL 是一种服务端请求伪造风险

**现象。** 没有现象,直到有人用它读走你的云元数据端点或者一个内网服务。

**为什么。** URL 是模型挑的。如果被抓取的页面能影响模型(在这里能——见 A5),攻击者就可以把它引向 `http://169.254.169.254/` 或 `http://localhost:5432`。你的进程在网络边界**内部**,攻击者不在。

**怎么做。** 连接之前先解析主机名,拒绝私有、回环和链路本地地址段——而且**每次重定向之后都要重新检查**,因为一个公网主机名可以重定向到一个私有地址。DNS 解析要放到事件循环之外做,因为它是阻塞的(见 B1)。

**在哪。** `tools/web_fetch.py` 里的 `_is_private_ip` 和重定向后的重新检查;测试在 `tests/unit/test_web_fetch_ssrf.py`。

## D 部分 — 记账与配置

### D1 — 永远不要用字符串替换去改写模型 id

**现象。** 降级路径请求了一个不存在的模型,provider 直接拒绝这次调用。

**为什么。** 把 `claude-opus-4-7` 通过替换子串变成 `claude-sonnet-4-7`,看起来像一次合理的"降一档"。它造出的是一个从未发布过的 id。这些命名方案不是可组合的。

**怎么做。** 维护显式的有序列表,在包含当前值的那个列表里往下走一步。任何不在列表里的值原样保留——一个没降级的模型只是比预期贵,这比命名一个端点会直接拒绝的东西好得多。

**每一种你支持的命名约定都要有一份自己的列表。** 同一个模型会因为配置的后端不同而表现为裸 id、CLI 别名、或者带厂商前缀的形式;只用一种约定写成的单一列表会一个都匹配不上,于是你的降级逻辑变成静默的空操作。

**在哪。** `llm/routing.py` 里的 `DEGRADE_CHAINS` 和 `degrade_model`。

### D2 — 未知模型按家族定价,而且要往上取

**现象。** 一个新的模型预览版被套上了价格表的默认值,于是要么预算上限失去意义,要么起飞前的估算错得离谱。

**为什么。** 模型目录变化的速度快过任何硬编码的价格表。

**怎么做。** 先查精确 id;查不到就按子串匹配家族提示(`flash-lite`、`flash`、`haiku`、`mini`、`opus`……),顺序上先具体后笼统;完全匹配不上就回退到一个中到偏贵的档位。高估的代价是提前停止,这是可恢复的;低估的代价是花掉你没打算花的钱。

**在哪。** `llm/routing.py` 里的 `PRICE_TABLE`、`_FAMILY_PRICE_HINTS`、`_FALLBACK_PRICE`。

### D3 — 一个限制不再是限制时,要说清楚

**现象。** 用户在订阅制后端上设了 `budget_usd`,并相信自己有一个美元上限。他并没有。

**为什么。** 在固定月费的订阅下,没有任何东西按 token 计费。CLI 报告的那个数字是一个**等价** API 成本,所以这个上限管的是一个仪表,不是钱。它仍然能抓住一次跑飞的会话,这有用——但真正的限制是墙钟时间和 idea 数量。

**怎么做。** 在这个设置出现的每一个地方都记录它含义的改变,并指名那些**真正**起作用的设置。**一个在不同配置之间静默改变含义的限制,比没有限制更糟,因为它制造虚假的安全感。**

**在哪。** `config/default.toml` 里 `budget_usd` 的注释,以及 README 的订阅后端一节。

### D4 — 深合并的配置加上换掉的后端,等于被拒绝的模型 id

**现象。** 换了 `provider` 之后,一部分 agent 正常、另一部分报"未知模型",看起来毫无规律。

**为什么。** 配置是分层深合并的,所以任何你没有覆盖的键都保留它的默认值。当那个默认值是为另一个 provider 写的时,残留的键会被原样发到新端点并被拒绝。只有那些你恰好覆盖了的 agent 是正常的。

**怎么做。** 在预检时校验:用"看起来像属于另一个 provider"的启发式规则检查每一个配置的模型 id,在启动时和 `doctor` 里发出警告,让用户在**第一次模型调用之前**就发现,而不是在跑了几分钟之后。写文档说"要全部覆盖"是必要的,但不充分——没人会及时读到它。

**在哪。** `llm/provider.py` 里的 `check_models`,由 `doctor` 和每次 `run` 调用。

### D5 — 输出 token 上限要按答案的形状来定,不要按模型的习惯

**现象。** 一个结构化记录在 JSON 中途被截断,解析失败。而且只在啰嗦或者重推理的模型上发生。

**为什么。** 输出上限管的是模型吐出的所有东西。一个带几个长散文字段加一个引用数组的记录,本身就确实很大,而一个会先长篇推理再作答的模型可能在对象中途就用完了空间。结果不是 provider 报的错误——而是一个语法上无效的参数字符串。

**怎么做。** 从 schema 的最坏情况渲染出发去定这个上限并留出余量,而不是从"多数模型通常产出多少"出发。当你把它调高时,把原因写在注释里;否则这个数字看起来很随意,总会有人再把它调回去。

**在哪。** `agents/generation.py` 里的 `max_output_tokens=8192`,理由写在旁边。
